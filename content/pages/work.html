The full story

PyTorch had no CI that tested Windows with a GPU. I led the design of a harness that provisions a GPU-backed Windows VM inside a Kubernetes pod on demand, triggered straight from GitHub Actions. The default runner model needs inbound access to the cluster, so I built a pull-based job service instead, where runners ask for work over an outbound connection.

Because the jobs run on our own hardware, I ran a STRIDE-based threat and vulnerability analysis and used it to set Kubernetes network policies and a gateway that screens jobs before they reach the compute cluster. When PyTorch moved to an out-of-tree CI model, I redesigned the core service to support it without pipeline downtime.
